# RAG와 자격판정 흐름

## 책임 분리

질문 이해: 사용자의 자연어 목적과 상황을 정책 탐색 조건으로 정규화한다.

정책 후보 선정: 선택 분야, 정책 메타데이터, 구조화 Rule로 정책 후보를 선정한다.

정책 근거 조회: 선정 또는 평가된 정책의 CSV RAG 문서, 공식 출처 URL, 검증일을 조회한다.

조건 구조화: 원문에서 조건 후보, 비교 연산자, 기준값, 필수 여부, 원문 위치를 추출한다.

D3 파생 Rule 후보는 공식 URL과 관리자 검수 기준본의 근거 위치를 연결한다. 공식 페이지의 조항 좌표가 확인되지 않은 경우 위치를 임의 생성하지 않으며 `OFFICIAL_CONFIRMATION_REQUIRED` 상태를 유지한다.

결정론적 조건 비교: 검증된 구조화 조건과 사용자 답변을 비교한다.

신청 가능성 상태 계산: 충족, 불충족, 미확인 조건으로 `LIKELY_ELIGIBLE`, `LIKELY_INELIGIBLE`, `NEEDS_CONFIRMATION` 등을 계산한다.

평가 생명주기 상태 계산: 정책 변경, 답변 충돌, 미평가 상태를 `ACTIVE`, `STALE`, `CONFLICTED`, `NOT_EVALUATED`로 관리한다.

근거 조립: 판정에 사용한 조건과 원문 위치, `policy_version`을 연결한다.

자연어 설명: 판정 결과와 근거를 사용자에게 이해 가능한 문장으로 설명한다.

## RAG의 역할과 한계

RAG는 구조화 메타데이터와 Rule Engine으로 이미 선정 또는 평가된 정책의 승인된 공식 근거 원문을 찾는 데 사용한다. RAG는 정책 자격 후보를 만들지 않는다. 검색 결과가 없거나 출처가 부족하면 정책을 생성하지 않는다. 검색 점수와 최종 판정 근거는 분리해 저장한다.

현재 입력은 `08_policy_document.csv`의 38개 문서다. `embedding`은 아직 생성하지 않으며, 문서 DTO는 추후 청크·임베딩 단계의 입력으로만 사용한다. 요약 문서이므로 상세 기준 확인이 필요한 답변은 반드시 `source_url`의 공식 안내를 함께 제시한다.

현재 RAG 검색 API와 vector repository는 구현되지 않았다. 따라서 빈 vector를 조회하는 런타임 경로도 없다. 후속 검색 API는 embedding 준비 여부를 먼저 확인하고, 준비되지 않았으면 vector 검색을 실행하지 않은 채 `INSUFFICIENT_EVIDENCE`와 빈 citations를 반환해야 한다. CSV 요약문을 vector 검색 결과인 것처럼 간주하지 않는다.

## LLM의 역할과 한계

LLM은 질문 이해, 조건 추출 보조, 행정 용어 설명, Rule 결과 요약, RAG 근거 기반 답변 생성에 사용할 수 있다. 정책 문서는 명령이 아닌 데이터로 취급한다. LLM 응답 문자열만으로 자격을 확정하지 않는다.

LLM 출력은 `app.llm.AIOutput` 계약을 따른다. 근거가 부족하면 `INSUFFICIENT_EVIDENCE`, LLM 호출이 실패하면 `LLM_UNAVAILABLE`, 추가 정보가 필요하면 `NEEDS_CONFIRMATION`을 반환하고 정책 사실을 생성하지 않는다.

## 근거 없는 생성 방지

출처 URL과 근거 문구가 없는 조건은 확정 판정 근거로 사용하지 않는다. Rule의 명시적 `evaluation_mode`가 `OFFICIAL_CONFIRMATION_REQUIRED`이면 기대값 문자열과 무관하게 결정형 계산에서 제외한다. 설명은 판정 결과를 바꾸지 않는다.

## 정책 버전과 판정 연결

판정은 사용한 `policy_version`과 사용자 정보 버전을 기록한다. 정책 원문이나 구조화 조건이 변경되면 기존 평가는 `STALE`로 처리한다.

## 검색 실패 처리

근거가 충분한 정책을 찾지 못하면 검색 범위와 조건을 안내한다. 평가 요청이 유효하지만 아직 판정하지 않은 경우는 `NOT_EVALUATED`로 남기고, 정책 데이터 자체가 사용할 수 없으면 API 오류 `POLICY_UNAVAILABLE`을 반환한다.

## 정보 부족 처리

필수 정보가 없으면 `NEEDS_CONFIRMATION`으로 처리하고 필요한 값과 확인 방법을 안내한다. null 또는 미입력을 자동 불충족으로 변환하지 않는다.

## 답변 충돌 처리

새 답변이 이전 답변과 충돌하면 충돌 필드를 기록한다. 해결 전에는 영향받은 판정을 확정 상태로 제공하지 않는다.

## 정책 변경 처리

원문 해시, `policy_version`, 조건 버전 변경을 감지한다. 변경된 조건에 필요한 정보만 다시 묻고, 변경 전후 판정 근거를 추적한다.

## D4 문서 가공 경계

정책 문서는 제목·조항·문단과 표 행 경계를 보존해 Chunk로 분리한다. 신청 대상, 신청 기간, 신청 방법, 제출 서류, 혜택, 문의 같은 의미 유형이 한 문장 안에 둘 이상 섞이면 `REVIEW_REQUIRED`로 표시하며 임베딩 입력에서 제외한다. 연락처 Chunk도 개인정보·불필요한 업무 연락처 검수를 위해 기본 `REVIEW_REQUIRED`로 둔다.

모든 Chunk는 `policy_id`, `document_id`, `source_url`, `source_location`, `content_hash`를 포함한다. 표는 escaped pipe를 보존하고 헤더를 각 행 값과 결합해 행별 Chunk로 만들며, 열 개수가 맞지 않으면 `REVIEW_REQUIRED`로 처리한다. Chunk의 정책 ID, 문서 유형과 URL은 부모 문서와 일치해야 한다. 임베딩 Seed는 승인 Chunk만 필터링해 포함하고 같은 문서의 검수 필요 Chunk는 제외한다. D4는 임베딩 입력 Seed까지만 생성하며 벡터 생성, pgvector 적재와 검색 API는 구현하지 않는다.
