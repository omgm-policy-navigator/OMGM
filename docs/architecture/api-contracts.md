# Backend API Contracts

## Contract Status

This document is the Phase B0 backend API draft. Only `GET /health` is implemented. Other endpoints define mockable contracts so frontend, backend, and data-pipeline work can proceed without sharing internal entities.

Base URL for local development: `http://localhost:8000`.

## API Version Strategy

MVP endpoints use `/api/...` without a version prefix. Breaking changes after MVP must add a new prefix such as `/api/v2/...` while keeping `/api/...` stable until clients migrate.

## Common Rules

- Request and response bodies use JSON unless the endpoint is explicitly SSE.
- API response schemas are DTOs and must not be SQLAlchemy entities.
- Unknown values are omitted or returned as `null` with an explicit status. They are not converted to `false` or `0`.
- Dates and timestamps use ISO 8601 strings.
- Policy and evaluation responses include `policyVersionId` where eligibility depends on policy data.
- Sensitive user facts are minimized in responses and must not be logged.
- Anonymous sessions are generated by the backend and transported only through an HttpOnly, SameSite cookie. Production cookies must be `Secure`; local HTTP development may omit `Secure` only in `APP_ENV=local`.
- Clients must not create, read, or submit session IDs in JSON.
- Unsafe cookie-authenticated methods must validate `Origin` against the configured frontend origins. `SameSite=Lax` is the cookie baseline; Origin validation is the CSRF protection for same-site POST, PATCH, PUT, and DELETE requests.

## Error Response

All handled application errors return this shape:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Requested resource was not found."
  }
}
```

`details` is optional. It is present when the error is safe and useful for clients, such as request validation failures. Internal stack traces and raw exception messages are never returned.

Validation error example:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "details": [
      {
        "location": ["body", "value"],
        "message": "Input should be a valid integer.",
        "type": "int_parsing"
      }
    ]
  }
}
```

Unexpected error example:

```json
{
  "error": {
    "code": "INTERNAL_ERROR",
    "message": "An unexpected error occurred."
  }
}
```

Unexpected exceptions must be logged server-side with stack trace and limited request metadata: HTTP method, route path, request ID or trace ID when available, and exception type. Logs must not include request bodies, cookies, session IDs, Authorization headers, full query strings, or sensitive user facts such as income and asset values.

### Error Codes

| Code | HTTP status | Meaning |
| --- | ---: | --- |
| `VALIDATION_ERROR` | 422 | Request body, path, or query parameters failed validation. |
| `CONFIGURATION_ERROR` | 500 | Backend configuration is invalid. |
| `SESSION_NOT_FOUND` | 404 | Anonymous or account session does not exist. |
| `POLICY_NOT_FOUND` | 404 | Requested policy does not exist. |
| `POLICY_UNAVAILABLE` | 503 | Policy data or evidence is not available enough to evaluate. |
| `EVALUATION_NOT_FOUND` | 404 | Requested evaluation does not exist. |
| `CONFLICTED_FACTS` | 409 | New user facts conflict with existing confirmed facts. |
| `RATE_LIMITED` | 429 | Client exceeded allowed request volume. |
| `INTERNAL_ERROR` | 500 | Unexpected server error with safe public message. |

Missing user information is not an error when the request itself is valid. Evaluation endpoints return `200` with `eligibilityStatus: "NEEDS_CONFIRMATION"` and required follow-up questions.

## Draft Endpoints

### `POST /api/session`

Creates an anonymous session owned by the backend. The backend generates the session ID and returns it only as a cookie.

Request: no body.

Response `201`:

```json
{
  "expiresAt": "2026-08-06T12:00:00Z"
}
```

Headers:

```http
Set-Cookie: anonymous_session=<random>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

Session lifecycle:

- TTL is 24 hours.
- Expiry is not sliding in B0 contracts. Later requests do not extend the session unless a later phase explicitly changes the contract.
- Multiple tabs in the same browser profile share the same anonymous session cookie.
- If a valid session already exists, `POST /api/session` returns `200` with the current `expiresAt` and does not rotate the cookie.
- Production and HTTPS development responses include `Secure`. Local HTTP development may omit `Secure` only in `APP_ENV=local`.

### `DELETE /api/session`

Deletes the current anonymous session and clears the cookie. Server-side conversation state, user facts, and evaluation records linked only to that anonymous session become inaccessible immediately and are hard-deleted unless a later retention policy explicitly replaces this behavior.

Request: no body.

Response `204`: no body.

Headers:

```http
Set-Cookie: anonymous_session=; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=0
```

### `POST /api/session/reset`

Starts a new diagnostic session by invalidating the existing anonymous session and issuing a new cookie. Existing conversation state, user facts, and evaluations are not accessible from the new session.

Request: no body.

Response `201`:

```json
{
  "expiresAt": "2026-08-06T12:00:00Z"
}
```

Headers:

```http
Set-Cookie: anonymous_session=<new-random>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

### `GET /api/policies`

Lists policy summaries using filters owned by the backend.

Query parameters:

| Name | Required | Meaning |
| --- | --- | --- |
| `region` | no | Administrative region filter. |
| `lifeEvent` | no | User life event such as `engaged` or `newlywed`. |
| `cursor` | no | Pagination cursor. |
| `limit` | no | Page size. |

Pagination:

- `limit` default: 20.
- `limit` maximum: 100.
- `cursor` is an opaque string. Clients must not parse or generate it.
- Invalid cursor returns `VALIDATION_ERROR` with HTTP 422.
- Sort order is `publishedAt DESC`, then `policyId ASC` as a stable tie-breaker.

Response `200`:

```json
{
  "items": [
    {
      "policyId": "policy_123",
      "title": "신혼부부 주거 지원",
      "agency": "서울시",
      "region": "서울",
      "status": "ACTIVE",
      "policyVersionId": "policy_version_123"
    }
  ],
  "nextCursor": null
}
```

### `POST /api/evaluations`

Evaluates policies using verified structured rules and current user facts.

Headers:

| Name | Required | Meaning |
| --- | --- | --- |
| `Idempotency-Key` | yes | Opaque client-generated key for retry-safe creation. |

Request:

```json
{
  "policyIds": ["policy_123"]
}
```

The current session is resolved from the `anonymous_session` cookie.

Idempotency:

- Repeating the same `Idempotency-Key` for the same session returns the original response.
- Reusing the same `Idempotency-Key` with a different request body returns `VALIDATION_ERROR` with HTTP 422.
- Evaluation results are returned in the same order as the requested `policyIds`.
- The evaluation input fingerprint is `session cookie identity + factVersion + sorted(policyIds) + policyVersionIds + ruleEngineVersion`. The backend may reuse an active evaluation with the same fingerprint, but the API-visible idempotency guarantee is keyed by `Idempotency-Key`.

Response `200`:

```json
{
  "items": [
    {
      "evaluationId": "eval_123",
      "policyId": "policy_123",
      "eligibilityStatus": "NEEDS_CONFIRMATION",
      "evaluationState": "ACTIVE",
      "policyVersionId": "policy_version_123",
      "factVersion": "facts_v2",
      "coverage": {
        "requiredKnown": 2,
        "requiredTotal": 3
      },
      "satisfied": ["region"],
      "unsatisfied": [],
      "needsConfirmation": ["HOUSEHOLD_INCOME_RANGE"],
      "nextQuestions": ["Q_HOUSEHOLD_INCOME_RANGE"]
    }
  ]
}
```

Allowed eligibility statuses:

- `LIKELY_ELIGIBLE`
- `NEEDS_CONFIRMATION`
- `AVAILABLE_LATER`
- `LIKELY_INELIGIBLE`
- `OFFICIAL_CONFIRMATION_REQUIRED`

Allowed evaluation states:

- `ACTIVE`
- `STALE`
- `CONFLICTED`
- `NOT_EVALUATED`

## Deferred API Areas

Saved policy and notification contracts are intentionally not fixed in B0. They depend on unresolved identity, anonymous-session retention, notification channel, browser permission, and data-retention decisions.

## Mock Contract Rules

Mocks must preserve the response envelopes, status strings, and null handling defined here. Mock data must be synthetic and must not include real personal data or real application records.

### `GET /health/ready`

Returns process readiness and verifies that PostgreSQL accepts a simple query. `GET /ready` remains as a compatibility alias. This endpoint is intended for local and container readiness checks; it does not expose connection strings or database error details.

Response `200`:

```json
{
  "status": "ready",
  "service": "omgm-backend",
  "environment": "local",
  "database": "connected"
}
```

Response `503` when PostgreSQL cannot be reached:

```json
{
  "status": "not_ready",
  "service": "omgm-backend",
  "environment": "local",
  "database": "unavailable"
}
```
