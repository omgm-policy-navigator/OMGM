# Backend API Contracts

## Contract Status

This document tracks implemented backend API contracts. Health endpoints were implemented in B1, policy catalog read endpoints were implemented in B2, and anonymous session/user fact endpoints were implemented in B3. Other endpoints remain draft contracts so frontend and backend work can proceed without sharing internal entities.

Base URL for local development: `http://localhost:8000`.

## API Version Strategy

MVP backend application endpoints use the `/api/v1/...` prefix. Health endpoints remain unversioned because they are infrastructure probes.

## Common Rules

- Request and response bodies use JSON unless the endpoint is explicitly SSE.
- API response schemas are DTOs and must not be SQLAlchemy entities.
- Unknown values are omitted or returned as `null` with an explicit status. They are not converted to `false` or `0`.
- Dates and timestamps use ISO 8601 strings.
- Policy and evaluation responses include `policyVersionId` where eligibility depends on policy data.
- Sensitive user facts are minimized in responses and must not be logged.
- Anonymous sessions are generated by the backend and transported only through an HttpOnly, SameSite cookie.
- Production cookies must be `Secure`; local HTTP development may omit `Secure` only in `APP_ENV=local`.
- Clients must not create, read, or submit session IDs in JSON, headers, URLs, or query parameters.
- Unsafe cookie-authenticated methods must validate `Origin` against the configured frontend origins.

## Error Response

All handled application errors return this shape:

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Requested resource was not found."
  }
}
```

`details` is optional. It is present when the error is safe and useful for clients, such as request validation failures. Internal stack traces and raw exception messages are never returned.

Validation error example:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Request validation failed.",
    "details": [
      {
        "location": ["body", "value"],
        "message": "Input should be a valid integer.",
        "type": "int_parsing"
      }
    ]
  }
}
```

Unexpected exceptions must be logged server-side with limited request metadata only: HTTP method, route path, request ID or trace ID when available, and exception type. Logs must not include request bodies, cookies, session IDs, Authorization headers, full query strings, or sensitive user facts.

### Error Codes

| Code | HTTP status | Meaning |
| --- | ---: | --- |
| `VALIDATION_ERROR` | 422 | Request body, path, or query parameters failed validation. |
| `CONFIGURATION_ERROR` | 500 | Backend configuration is invalid. |
| `SESSION_NOT_FOUND` | 404 | Anonymous or account session does not exist. |
| `SESSION_ORIGIN_FORBIDDEN` | 403 | Cookie-authenticated request origin is not allowed. |
| `POLICY_NOT_FOUND` | 404 | Requested policy does not exist. |
| `POLICY_UNAVAILABLE` | 503 | Policy data or evidence is not available enough to evaluate. |
| `EVALUATION_NOT_FOUND` | 404 | Requested evaluation does not exist. |
| `CONFLICTED_FACTS` | 409 | New user facts conflict with existing confirmed facts. |
| `RATE_LIMITED` | 429 | Client exceeded allowed request volume. |
| `INTERNAL_ERROR` | 500 | Unexpected server error with safe public message. |

Missing user information is not an error when the request itself is valid. Evaluation endpoints return `200` with `eligibilityStatus: "NEEDS_CONFIRMATION"` and required follow-up questions.

## Implemented Health Endpoints

### `GET /health/live`

Returns backend process liveness without checking PostgreSQL or other dependencies. `GET /health` remains as a compatibility alias.

Response `200`:

```json
{
  "status": "ok",
  "service": "omgm-backend",
  "environment": "local"
}
```

### `GET /health/ready`

Returns process readiness and verifies that PostgreSQL accepts a simple query. `GET /ready` remains as a compatibility alias. Responses include `Cache-Control: no-cache, no-store, must-revalidate`.

Response `200`:

```json
{
  "status": "ready",
  "service": "omgm-backend",
  "environment": "local",
  "database": "connected"
}
```

Response `503`:

```json
{
  "status": "not_ready",
  "service": "omgm-backend",
  "environment": "local",
  "database": "unavailable"
}
```

Returns policy categories sorted by catalog order.

Response `200`:


Returns approved and active policy detail with institution, source, and application-period metadata.

## Implemented Anonymous Session Endpoints

### `POST /api/v1/session`

Creates or returns the current anonymous session. The backend generates a UUID4 session token and returns it only in the `anonymous_session` cookie. Clients must not send or receive session IDs in JSON, headers, URLs, or query parameters.

Request body is optional, but any client-supplied session identifier such as `sessionId`, `session_id`, or `anonymous_session` is rejected with `VALIDATION_ERROR`. Client-supplied session headers such as `X-Session-Id` are also rejected.

Response `201` when a new session is created, or `200` when the existing cookie session is still valid:

```json
{
  "status": "session_created"
}
```

Headers include:

```http
Set-Cookie: anonymous_session=<uuid4>; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

Production and non-local environments set `Secure`. `APP_ENV=local` may omit `Secure` for local HTTP development. Absolute expiry defaults to 24 hours. Idle expiry defaults to 60 minutes and never extends beyond the absolute expiry.

### `GET /api/v1/session`

Returns expiry metadata for the current anonymous session resolved from the cookie. Missing, deleted, or expired sessions return `SESSION_NOT_FOUND` with HTTP 404.

Response `200`:

```json
{
  "status": "session_active",
  "expiresAt": "2026-08-07T00:00:00Z",
  "idleExpiresAt": "2026-08-06T11:00:00Z"
}
```

### `DELETE /api/v1/session`

Deletes the current anonymous session and clears the cookie. Linked `user_fact` rows are deleted by database cascade.

Response `204`: no body.

### `GET /api/v1/session/facts`

Returns facts for the current anonymous session only.

Response `200`:

```json
[
  {
    "conditionKey": "region",
    "value": "Seoul",
    "source": "manual",
    "confirmed": true,
    "updatedAt": "2026-08-06T10:00:00Z"
  }
]
```

### `PUT /api/v1/session/facts/{condition_key}`

Creates or updates a fact for the current anonymous session only. The route path condition key is authoritative; clients cannot set another session or owner in JSON.

Request:

```json
{
  "value": "Seoul",
  "confirmed": true,
  "source": "manual"
}
```

Response `200` returns the stored fact DTO.

## Draft Endpoints

### `POST /api/v1/session/reset`

Starts a new diagnostic session by invalidating the existing anonymous session and issuing a new cookie. Existing conversation state, user facts, and evaluations are not accessible from the new session.

Response `201`:

```json
{
  "status": "session_created"
}
```

### `GET /api/v1/policies`

Lists policy summaries using filters owned by the backend.

Query parameters:

| Name | Required | Meaning |
| --- | --- | --- |
| `region` | no | Administrative region filter. |
| `lifeEvent` | no | User life event such as `engaged` or `newlywed`. |
| `cursor` | no | Pagination cursor. |
| `limit` | no | Page size. |

Pagination:

- `limit` default: 20.
- `limit` maximum: 100.
- `cursor` is an opaque string. Clients must not parse or generate it.
- Invalid cursor returns `VALIDATION_ERROR` with HTTP 422.
- Sort order is `publishedAt DESC`, then `policyId ASC` as a stable tie-breaker.

Response `200`:

```json
{
  "items": [
    {
      "policyId": "policy_123",
      "title": "Newlywed Housing Support",
      "agency": "Seoul Metropolitan Government",
      "region": "Seoul",
      "status": "ACTIVE",
      "policyVersionId": "policy_version_123"
    }
  ],
  "nextCursor": null
}
```

### `POST /api/v1/conversations`

Starts a policy navigation conversation for an anonymous session. The current session is resolved from the `anonymous_session` cookie.

Request:

```json
{
  "initialMessage": "Find housing support policies for newlyweds in Seoul."
}
```

Response `201`:

```json
{
  "conversationId": "conv_123",
  "nextQuestions": [
    {
      "questionId": "q_region",
      "factKey": "region",
      "prompt": "Please confirm your residential region.",
      "answerType": "single_select",
      "required": true,
      "options": [
        {"label": "Seoul", "value": "SEOUL"},
        {"label": "Gyeonggi", "value": "GYEONGGI"},
        {"label": "Incheon", "value": "INCHEON"}
      ]
    }
  ]
}
```

### `POST /api/v1/conversations/{conversationId}/answers`

Stores normalized user facts collected through a conversation.

Request:

```json
{
  "answers": [
    {
      "questionId": "q_region",
      "factKey": "region",
      "value": "SEOUL",
      "confirmed": true
    }
  ]
}
```

Response `200`:

```json
{
  "factVersion": "facts_v2",
  "conflicts": [],
  "nextQuestions": []
}
```

### `POST /api/v1/evaluations`

Evaluates policies using verified structured rules and current user facts. The current session is resolved from the `anonymous_session` cookie.

Headers:

| Name | Required | Meaning |
| --- | --- | --- |
| `Idempotency-Key` | yes | Opaque client-generated key for retry-safe creation. |

Request:

```json
{
  "policyIds": ["policy_123"]
}
```

Response `200`:

```json
{
  "items": [
    {
      "evaluationId": "eval_123",
      "policyId": "policy_123",
      "eligibilityStatus": "NEEDS_CONFIRMATION",
      "evaluationState": "ACTIVE",
      "policyVersionId": "policy_version_123",
      "factVersion": "facts_v2",
      "coverage": {
        "requiredKnown": 2,
        "requiredTotal": 3
      },
      "satisfied": ["region"],
      "unsatisfied": [],
      "needsConfirmation": ["HOUSEHOLD_INCOME_RANGE"],
      "nextQuestions": ["Q_HOUSEHOLD_INCOME_RANGE"]
    }
  ]
}
```

Allowed eligibility statuses:

- `LIKELY_ELIGIBLE`
- `NEEDS_CONFIRMATION`
- `AVAILABLE_LATER`
- `LIKELY_INELIGIBLE`
- `OFFICIAL_CONFIRMATION_REQUIRED`

Allowed evaluation states:

- `ACTIVE`
- `STALE`
- `CONFLICTED`
- `NOT_EVALUATED`

### `GET /api/v1/evaluations/{evaluationId}`

Returns an evaluation result and evidence references.

Response `200`:

```json
{
  "evaluationId": "eval_123",
  "policyId": "policy_123",
  "eligibilityStatus": "NEEDS_CONFIRMATION",
  "evaluationState": "ACTIVE",

      "sourceLabel": "Income requirement",
      "policyVersionId": "policy_version_123"

  ]
}
```

Response `200`:

```json
      "id": "policy_123",
```

## Deferred API Areas

Saved policy and notification contracts are intentionally not fixed in B0. They depend on unresolved identity, anonymous-session retention, notification channel, browser permission, and data-retention decisions.

## Mock Contract Rules

Mocks must preserve the response envelopes, status strings, and null handling defined here. Mock data must be synthetic and must not include real personal data or real application records.
