# 개발 추적 기준

## Phase 상태값

- `PLANNED`: 범위와 시작 조건이 정의됨.
- `IN_PROGRESS`: 브랜치가 생성되고 구현이 진행 중.
- `VALIDATING`: 실행, 테스트, 문서 링크, Git ignore를 검증 중.
- `DONE`: 검증을 통과하고 커밋·push가 완료됨.
- `BLOCKED`: 외부 접근, 권한, 미확정 설계로 완료할 수 없음.

## Phase 시작 조건

- 대상 저장소와 브랜치 확인.
- 미커밋 변경 없음.
- 설계 자료 확인.
- 이번 Phase 포함·제외 범위 정의.

## Phase 완료 조건

- 코드와 문서가 같은 책임 경계를 설명한다.
- README 명령이 실제로 동작한다.
- Health Check와 최소 테스트가 통과한다.
- 비밀정보와 로컬 산출물이 Git에서 제외된다.
- 검증 결과와 남은 위험이 Phase 문서에 기록된다.

## 코드·테스트·문서 동기화

모듈 경계, 판정 상태, 환경변수, 실행 명령이 바뀌면 `README.md`, `AGENTS.md`, 관련 `docs/` 문서를 함께 갱신한다.

## 브랜치 규칙

기능 브랜치는 `feat/<scope>` 또는 `chore/<scope>` 형태를 사용한다. Phase 0 브랜치는 `feat/phase-0-project-foundation`이다.

## PR 규칙

PR에는 변경 범위, 검증 명령, 문서 링크, 남은 위험, 다음 Phase 입력물을 포함한다.

## 설계 변경 추적

확정 설계와 다른 구현 결정을 내리면 관련 문서를 먼저 갱신한다. 되돌리기 어려운 결정이면 ADR을 작성한다.

## ADR 작성 조건

서비스 경계, 데이터 소유권, 판정 방식, LLM 책임, 보안 저장 방식, 인프라 선택이 바뀔 때 작성한다. 단순 폴더 생성과 라이브러리 설치는 ADR 대상이 아니다.

## Troubleshooting 작성 조건

실제 문제가 발생하고 증상, 환경, 재현, 원인, 해결, 검증이 확인된 경우에만 `docs/troubleshooting/` 아래에 작성한다. 추측성 문서는 만들지 않는다. Phase 0에는 기록할 실제 장애 해결 문서가 없어 디렉터리를 생성하지 않는다.

## 정책 계약 변경 영향 분석

정책 조건, 판정 상태, 사용자 답변 필드, 정책 버전 계약이 바뀌면 판정, 설명, 저장, 보안, 테스트, 문서 영향을 함께 점검한다.
