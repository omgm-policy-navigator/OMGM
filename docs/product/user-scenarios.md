# 사용자 시나리오

## 1. 예비부부의 정책 탐색

사용자: 혼인신고 전인 예비부부.

사전 조건: 거주 예정 지역과 결혼 예정 시점 일부를 알고 있다.

목표: 혼인 전에도 준비할 수 있는 정책과 혼인신고 후 신청 가능한 정책을 구분해 확인한다.

정상 흐름: 사용자가 목적과 지역을 입력한다. 시스템은 혼인 상태, 예정일, 거주지, 소득 등 필요한 조건을 질문한다. 정책 후보를 검색하고 구조화 조건과 답변을 비교한다.

예외 흐름: 혼인신고일이 없으면 혼인신고일 필수 정책은 `NEEDS_CONFIRMATION`으로 표시한다.

시스템 결과: 정책명, 기관, 신청 가능 상태, 신청 시점, 부족 정보, 원문 출처를 제공한다.

신청 가능성 상태: `LIKELY_ELIGIBLE`, `NEEDS_CONFIRMATION`.

필요한 근거: 정책 원문, 신청 기준일, 대상자 조건.

## 2. 신혼부부의 정책 자격 확인

사용자: 혼인신고를 완료한 신혼부부.

사전 조건: 혼인신고일, 현재 거주지, 대략적인 소득 정보를 제공할 수 있다.

목표: 현재 신청 가능한 정책을 확인한다.

정상 흐름: 시스템은 혼인 기간, 거주지, 소득, 자산, 주택 여부를 정규화한다. 정책 후보를 검색하고 조건별 충족 여부를 계산한다.

예외 흐름: 소득이 기준을 초과하면 해당 정책은 `LIKELY_INELIGIBLE`로 표시하되 다른 정책 탐색은 계속한다.

시스템 결과: 충족 조건과 불충족 조건을 분리해 보여준다.

신청 가능성 상태: `LIKELY_ELIGIBLE`, `LIKELY_INELIGIBLE`.

필요한 근거: 혼인 기간 기준, 소득 기준, 거주 요건, 정책 버전.

## 3. 소득을 정확히 모르는 사용자

사용자: 소득 산정 기준을 정확히 모르는 사용자.

사전 조건: 소득 관련 질문에 "모르겠다" 또는 미확정 답변을 제공한다.

목표: 탈락 처리되지 않고 어떤 정보를 확인해야 하는지 안내받는다.

정상 흐름: 시스템은 해당 필드를 미확정으로 저장하고 소득 기준과 확인 가능한 서류를 안내한다.

예외 흐름: 사용자가 추정값을 제공하면 확정값이 아닌 미확정 값으로 취급한다.

시스템 결과: 해당 조건은 확인 필요로 표시하고 정보 보완 후 재판정한다.

신청 가능성 상태: `NEEDS_CONFIRMATION`.

필요한 근거: 정책 소득 기준, 필수 여부, 확인 서류.

## 4. 답변이 이전 정보와 충돌한 사용자

사용자: 이전에는 혼인신고 전이라고 답했지만 이후 혼인신고일을 입력한 사용자.

사전 조건: 동일 필드 또는 연관 필드에 이전 답변이 있다.

목표: 충돌을 해결하고 영향을 받은 판정만 다시 계산한다.

정상 흐름: 시스템은 충돌 필드를 기록하고 사용자에게 현재 상태를 재확인한다.

예외 흐름: 충돌 해결 전에는 관련 판정을 확정 상태로 제공하지 않는다.

시스템 결과: 기존 판정을 무효화하고 확정 답변 저장 후 재판정한다.

평가 생명주기 상태: 내부 `CONFLICTED`, 사용자에게는 재확인 요청.

필요한 근거: 변경 전후 답변, 변경 시점, 영향받은 조건.

## 5. 정책 기준이 변경된 뒤 다시 방문한 사용자

사용자: 이전 판정 결과를 다시 확인하는 사용자.

사전 조건: 정책 원문 또는 구조화 조건의 버전이 변경되었다.

목표: 최신 정책 기준으로 재판정한다.

정상 흐름: 시스템은 기존 평가를 `STALE`로 표시하고 변경된 조건만 식별한다.

예외 흐름: 변경된 조건에 필요한 사용자 정보가 없으면 추가 질문한다.

시스템 결과: 새 정책 버전 기준의 판정과 변경 근거를 제공한다.

평가 생명주기 상태: `STALE`, 이후 `ACTIVE`.

신청 가능성 상태: `LIKELY_ELIGIBLE`, `LIKELY_INELIGIBLE`, `NEEDS_CONFIRMATION`.

필요한 근거: 이전 정책 버전, 현재 정책 버전, 변경 조건.

## 6. 관련 정책을 찾지 못한 사용자

사용자: 특정 지역이나 조건에 맞는 정책을 찾는 사용자.

사전 조건: 검색 범위 내 정책 근거가 부족하다.

목표: 없는 정책을 생성하지 않고 검색 한계를 이해한다.

정상 흐름: 시스템은 검색 범위, 조건, 출처 부족을 설명한다.

예외 흐름: LLM이 정책명이나 조건을 추측하지 않는다.

시스템 결과: 검색 실패 또는 근거 부족 상태를 표시한다.

평가 생명주기 상태: `NOT_EVALUATED`. 정책 데이터 자체가 부족하면 API 오류 `POLICY_UNAVAILABLE`로 처리할 수 있다.

필요한 근거: 검색 조건, 검색 시점, 확인한 출처 범위.

## 7. 근거 원문을 확인하려는 사용자

사용자: 판정 이유를 신뢰하기 위해 원문을 확인하려는 사용자.

사전 조건: 판정 결과에 정책 후보와 출처가 연결되어 있다.

목표: 어떤 원문 문구가 어떤 조건에 쓰였는지 확인한다.

정상 흐름: 시스템은 조건별 원문 출처와 수집 시점을 제공한다.

예외 흐름: 원문 위치가 없는 구조화 조건은 확정 판정 근거로 사용하지 않는다.

시스템 결과: 정책 원문 URL, 버전, 조건별 근거를 표시한다.

상태: 기존 신청 가능성 상태와 평가 생명주기 상태 유지.

필요한 근거: 원문 URL, 원문 해시, 조건 근거 위치.
