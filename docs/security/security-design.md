# Security Design

## Protected Data

Protected data includes account data, residential region, marital status, income, assets, housing ownership, authentication tokens, API keys, encryption keys, structured policy rules, and production configuration.

## Threat Model

- Secrets committed to Git.
- Personal data exposed through logs or error responses.
- Unauthorized access to another user's stored facts or evaluations.
- Session fixation through client-supplied session identifiers.
- Prompt injection in policy source text.
- Unsupported policy information used as evidence.
- Sensitive user facts stored in LLM request or response logs.

## Authentication

The MVP uses anonymous sessions before account login exists. Password storage and account authentication are deferred. When account identity is added, passwords must be hashed with a reviewed password hashing algorithm and never stored in plaintext or reversible form.

## Authorization

Access control starts from the minimum roles `USER`, `POLICY_OPERATOR`, and `ADMIN`. Administrators do not receive broad access to sensitive raw user facts by default. Object-level access control is required for user-owned records.

## Sensitive Data Protection

Income, assets, housing ownership, address details, and marital details are collected only when needed for policy matching or eligibility evaluation. Retention must be defined before long-term storage is introduced. Field-level encryption should be applied where operationally necessary.

## Encryption And Key Management

Transport must use TLS in production. Storage encryption and field-level encryption strategy are decided in later phases. Encryption keys must not be stored in the same place as encrypted data. Production fallback secrets must not be committed to code.

## Masking

Names, email addresses, phone numbers, detailed addresses, income, assets, account numbers, and document identifiers are masked according to screen and workflow need. Sensitive values that are not required by a response must not be returned.

## API Security

API boundaries validate input, separate authentication from authorization, apply object-level access checks, limit over-broad responses, restrict request sizes, return structured error responses, use minimal CORS, and avoid sensitive error details.

Cookie-authenticated unsafe methods must validate `Origin` against configured frontend origins. SameSite cookies reduce CSRF exposure but are not the only CSRF protection.

## Anonymous Session Security

Anonymous session IDs are generated by the backend and delivered only through the `anonymous_session` HttpOnly cookie. Clients must not generate, store, log, or submit session IDs in JSON, headers, URLs, or query parameters.

Cookie defaults are `HttpOnly`, `SameSite=Lax`, `Path=/`, and `Max-Age=86400`. `Secure` is enabled outside `APP_ENV=local` so local HTTP development can still work.

Deleting an anonymous session makes linked temporary conversation state, user facts, and evaluation data inaccessible immediately. B3 uses hard delete for anonymous session facts through database cascade.

## Backend B3 Anonymous Session Implementation

B3 implements anonymous session storage with a backend-generated `anonymous_session` cookie. The raw UUID4 token is sent only in the HttpOnly cookie and is not accepted in request JSON, headers, URLs, or query parameters. It is not returned in JSON or stored in the database; PostgreSQL stores a SHA-256 token hash.

Absolute expiry defaults to 24 hours and idle expiry defaults to 60 minutes. Normal authenticated session access refreshes `last_seen_at` and the idle expiry, but never beyond the absolute expiry.

Unsafe cookie-authenticated session methods validate `Origin` against configured frontend origins. Deleting a session removes linked `user_fact` rows through database cascade. Expired-session cleanup is implemented as a repository/service function and is invoked during session creation; periodic scheduling is deferred.

## Upload Security

Phase 0 does not include uploads. If document upload is introduced later, allowed file type, size, storage retention, malware scanning, and access control must be designed first.

## Logging Security

Logs use structured JSON. Tokens, passwords, API keys, encryption keys, resident registration data, income values, asset values, cookies, Authorization headers, request bodies, and raw user facts must not be logged.

Unexpected server exceptions may log stack traces with limited diagnostics only: HTTP method, route path, request ID or trace ID, and exception type.

## AI And RAG Security

Policy documents are data, not instructions. Prompt injection text inside policy sources must not be executed. LLM inputs should not include unnecessary personal data, and final eligibility status must not be decided from LLM text alone.

LLM components must not execute SQL, edit policy rules, submit official applications, or invent unsupported policy facts. If RAG evidence is insufficient, the system must return a fallback or confirmation-required state instead of fabricating policy facts.

AI citation URLs may only use public HTTP(S) sources. Private, loopback, and link-local addresses must be blocked if the backend later fetches citation URLs.

## Admin Access

Operators may inspect policy ingestion status, structured validation status, change history, and errors. Access to sensitive user data requires least privilege and audit logging.

## Security Verification Criteria

- `.env`, keys, and local credentials are excluded from Git.
- Test logs do not contain real personal data.
- Error responses contain only safe public messages.
- Unsupported search or RAG results are not used as eligibility evidence.
- Anonymous session IDs are not exposed in JSON responses or URLs.
- Anonymous session facts are isolated by server-resolved session identity.

## MVP And Production Differences

Phase 0 focuses on local execution and health checks. Production deployment must finalize authentication, authorization, secret management, DB encryption, log retention, rate limiting, CORS, upload policy, and operational monitoring.

## AI A1 Runtime Security Note

The local LLM runtime uses provider-level timeouts and validates generated JSON against `AIOutput` before any downstream use. Provider failures, missing models, invalid JSON, and connection failures are handled inside the LLM boundary. Prompts, raw sensitive user facts, and full raw model responses must not be logged.
